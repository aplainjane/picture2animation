# 阶段 01：角色结构设计

从一张角色图开始，识别可运动部件、连接关系和遮挡，形成设计者可修改的拆分与节点方案。本文件由主 `SKILL.md` 按需加载，具体执行说明以本文件为准。

输入：角色原画，以及已有的部件、节点或动作要求（如有）。

输出：部件标注与清单、叠加原图且可调整骨骼的网页、结构 JSON、素材处理建议，以及尚未确定的结构问题。

## 网页使用与交接卡

以下路径中的 `P` 为当前角色项目绝对路径，统一调用和目录约定见[项目产物与交接](../references/project-artifacts.md)。

- **调用工具**：`scripts/build_rig_editor.py` 复用 `assets/rig-editor.html`，输出建议命名为 `P/stage01-review.html`。
- **AI准备／提交**：原图 `P/input/character.png` 和基于该图制作的 `P/input/structure.json`；提交给生成器，不能用上一角色的节点坐标充数。
- **用户怎么用**：在原图上拖动节点，按需改名称、坐标、父子关系、关联部件和定位依据；可新增节点、撤销重做及缩放。先核对人体基础节点和角色自身左右。
- **保存与整阶段提交**：服务页设计改动自动保存。等待保存完成后点“确认设计并进入下一步”；“确认当前节点”、导出JSON和保存网页都只是局部操作或备份，不放行阶段。
- **产出在哪里**：网页在 `P/stage01-review.html`；最新草稿在 `P/stage01-review.workflow/draft.json`，有效整阶段结果在同目录 `confirmed.json`。原始 `structure.json` 不自动更新。
- **下一阶段拿什么**：阶段02先对该workflow执行 `check`，读取返回的 `confirmed_file` 中的 `design`，包含最终节点及结构；不读取最初的structure配置或截图重新猜点。

## 输入与范围

- 读取用户提供的原画或本地图片，记录实际像素尺寸。缺少图片时先索取图片，不根据旧案例编造当前角色的部件或坐标。
- 优先采用设计者提供的部件清单、边界、节点、命名及连接关系；区分已有设计与 AI 建议，不擅自覆盖已有设计。
- 结合已知动作需求决定拆分粒度。动作尚未确定时提供基础方案，把依赖具体动作的拆分列为可选项，不默认角色必须跑步。
- 本阶段先完成结构设计并等待人工在网页确认；只有本阶段 checkpoint 通过后，才可进入已实现且属于当前任务的下一阶段。

## 1. 识别部件与遮挡

观察实际图片，列出身体、服装、头发及配饰等可见部件，说明它们的连接处和遮挡关系。只列出该角色确实存在或运动确实需要的结构，不套用固定角色的部件清单。

将可见证据与推测分开：隐藏的肩、肘、髋等位置只能作为估计；无法从单张图确定的背面、纹样和隐藏肢体需要明确说明。

名称优先沿用设计者约定。自行命名时说明左右是角色自身左右还是画面左右；无法判断时可使用近侧、远侧等表述。用稳定 ID 关联后续标注、节点和素材。

## 2. 提出拆分边界

按运动需求拆分：需要相对转动、弯曲、独立摆动或改变前后关系的区域，才考虑独立处理。比较保持整体与拆分的收益，避免把所有视觉细节都切成独立图层。

- 接缝优先放在袖口、领口、腰线、裙摆、靴口等天然边界或遮挡处。
- 关节处说明需要的重叠与补底区域，避免两块素材仅沿边缘相接，转动后露洞。
- 区分刚性部件与柔性区域：饰品可绕挂点转动；头发、裙摆等可通过多节点或变形控制，不一定切成许多硬片。
- 纹样、蕾丝、复杂明暗等细节尽量随所属部件保留。
- 部件前后绘制关系单独记录，不用骨骼父子关系代替绘制顺序。动作可能改变遮挡时，说明需要动态顺序、遮罩或替换素材。

## 3. 提出节点与连接关系

骨骼节点表示运动支点和控制关系，部件表示可绘制素材，两者不要求一一对应。一个部件可受多个节点控制，一个节点也可带动多个部件。

- 完整人形角色默认采用 [人体基础骨架与 Spine 参考](../references/humanoid-skeleton.md) 的 18 个基础节点：总根、骨盆中心、腰、胸、颈、头，以及左右肩/肘/腕、左右髋/膝/踝。先完成人体骨架，再追加服装、头发和饰品等节点；不能因为人体关节被衣服遮挡，或现有切片没有单独的肢段，就省略相应节点。
- 结合实际原图推定隐藏的肩、肘、髋、膝等位置，并标为 `inferred`；设计者可移动节点、自定 ID、增设控制链。头像、裁剪或非人形等不适用完整骨架时，明确记录适用范围和缺项原因；设计者指定简化方案时保留该决定。完整人形交付前按参考清单检查节点语义与连接，不仅检查节点总数。
- 非身体部件按实际结构设置头发根部、帽尖根部、配饰挂点等锚点；柔性部件可提出控制链。
- 对每个节点记录 ID、类型、位置、父节点、关联部件及位置依据。没有父节点的根节点明确标识。
- 默认用原图像素坐标，左上角为原点，x 向右、y 向下；若使用裁剪、缩放或归一化坐标，记录变换关系，避免混用。
- 把节点位置、父子连接和运动约束作为可分别修改的设计项。隐藏关节位置、活动范围等估计值标为建议，不宣称已验证。

## 4. 判断素材处理方式

按部件逐项提出建议，而不是预设整张图统一切片或统一矢量化。

| 方案 | 判断依据 |
| --- | --- |
| 原画切片 | 现有像素足以表现目标运动，且保留纹样、笔触和明暗很重要 |
| 原画切片并补全遮挡 | 相对运动会露出原图中不存在的区域，需标出补全范围 |
| 局部 SVG 重绘 | 形状较简单，需要独立控制轮廓或表情，且可接受的风格匹配能够实现 |
| 替换姿势素材 | 手势、转头、透视或轮廓变化难以通过现有切片自然实现 |

SVG 可用于简单肢段、连接补片、眼睑或嘴形等，但复杂手掌、衣纹、脸部和发型需结合原画判断。SVG 是素材表达方式，弯曲仍需要节点、路径或网格等控制。说明重绘的具体区域、原因、接缝和风格匹配难点；本阶段只做规划。

## 5. 交付并吸收设计调整

### 生成骨骼预览与编辑网页

AI 先实际读取原画，提出部件和节点位置；网页负责展示与人工编辑，不自动识别图片。设计者已提供节点时直接载入其设计。按 [网页数据格式](../references/rig-editor-format.md) 写出 `structure.json`。

使用本 skill 自带的 `scripts/build_rig_editor.py` 和 `assets/rig-editor.html` 生成项目交付文件。下面路径均应换成实际路径；脚本路径相对本 skill 根目录：

```bash
python scripts/build_rig_editor.py --image character.png --config structure.json --out character-review.html
```

- 需要 Python 和 Pillow；优先使用已有运行环境。生成器内嵌图片与节点，输出网页可直接打开，无需服务器或网络。
- 图像按 EXIF 方向转正后内嵌；标注必须基于该方向和尺寸。传入原画，而不是节点截图或已经缩放的展示图。
- 不修改模板中的默认数据来适配单个角色。缺少初始节点时可省略 `--config` 生成手动标注网页，但应说明其尚未包含 AI 定位结果。
- 打开生成的网页供设计者预览。支持节点拖动、数值坐标编辑、自定义节点、父子关系、定位依据和关联部件编辑，包含撤销重做与缩放。
- 独立 HTML 的修改需要导出 JSON 或保存网页；由 skill 启动的本地审阅页会把修改保存到检查点项目的 `draft.json`。原始 `structure.json` 不被直接回写。
- 以 checkpoint 中人工实际确认的设计快照为后续依据，不从旧截图重猜坐标。导出或保存只产生副本，不能代替阶段确认。
- JSON 同时保留部件规划和未使用的扩展字段。部件区域轮廓的绘制编辑、自动识别和动作预览不属于当前骨骼编辑器能力。

### 配套交付

根据图片和用户当前关注点，提供便于设计者修改的结果：

- 部件方案：带编号的区域标注或示意，以及部件 ID、名称、边界、遮挡和拆分理由。
- 节点方案：可交互网页中叠加原图、节点和连接；区分可见定位与推测定位，以及建议、已调整、设计者已确认三种状态。确认操作由设计者执行，AI 初步定位默认是建议状态。
- 素材处理清单：关联到部件，列出保留原画、补底、SVG 重绘或替换姿势的建议及原因。
- 待定项：只列会影响当前结构设计的疑点，优先给出可比较的选项。

保留用户指定的节点和部件 ID，修订时同步标注、清单和连接关系。完成初步结构设计后进入下述人工检查点。

## Checkpoint：人工确认

生成器默认在 HTML 同级建立 `<网页文件名>.workflow/`，也可通过 `--project` 指定项目目录。每次重新生成代表新一轮审阅，会生成新的 `run_id`，因此恢复已有任务时应启动服务，不重新运行生成器覆盖设计。

1. 生成或恢复项目后，运行本 skill 的本地连接服务：

   ```bash
   python scripts/review_checkpoint.py serve --project character-review.workflow
   ```

   使用可持续运行的终端会话，或在 Windows 用 `Start-Process -WindowStyle Hidden` 后台启动，记录进程与日志。读取启动输出或项目 `server.json` 的 URL，在应用浏览器打开它；没有应用浏览器工具时提供实际可访问的本地 URL。不要用 `file://` 页面替代服务页面来声称已连接检查点。

2. 网页进入 `awaiting_review`。设计者调整节点与连接，服务自动保存草稿。名称、坐标、连接、导入、撤销重做等数据修改会撤销已有阶段确认；画布缩放与平移不影响确认。页面会显示保存中或保存失败；保存失败不得当作设计已交回。
3. 设计者点击“确认设计并进入下一步”。这是对当前整套骨骼布局的确认，服务将节点标为已确认，原子写入 `confirmed.json` 并更新 `workflow.json`。无需逐个节点点击确认。AI 不代点此按钮，不直接调用确认 API，也不自行制造确认文件。
4. 在当前任务仍执行时，用有界检查等待用户确认；每次等待最长 50 秒，默认 30 秒，便于保持沟通并响应新输入：

   ```bash
   python scripts/review_checkpoint.py wait --project character-review.workflow --timeout 30
   ```

   返回码 `0` 表示有效确认；`2` 表示仍等待或检查失败，结果为 JSON。一次等待超时不视为确认，可以在任务仍活动时继续有界等待。不要因为点击页面、看到绿色节点、普通下载或旧标识存在而跳过检查；也不要在任务已经结束时声称文件会自动唤醒 AI。
5. 放行前再次执行 `check`，读取返回的 `confirmed_file` 及其中 `design` 作为后续输入：

   ```bash
   python scripts/review_checkpoint.py check --project character-review.workflow
   ```

   检查本次 `run_id`、阶段、原图指纹与尺寸、修订号、设计摘要和当前草稿的一致性。旧任务的标识、确认后发生的修改、不完整写入或被改动的确认内容都不放行。

确认范围是骨骼布局 `skeleton-layout`：坐标、节点层级和关联部件。它不表示部件边界已精确分割或所有隐藏区域已补完。下一阶段仍需根据部件设计开展边界定位与拆图。

检查通过后，主流程可按当前任务加载 [阶段 02：角色拆图与表情分离](02-part-separation.md)，以确认设计为输入，不再要求重复口头确认。阶段 02 生成自己的审阅项目，不能覆盖本阶段文件。

会话恢复时先 `check`：通过则复用确认快照；未通过则恢复草稿、打开审阅页等待人工。每个项目仅运行一个服务；已有 `server.json` 时先检查记录的进程与 URL，能使用就复用，服务已结束才重新启动。停止本地服务时只处理本次记录的进程，保留项目文件。

## 完成条件

部件、节点与素材处理建议能够按 ID 相互对应；完整人形按人体基础骨架清单核对，缺项或例外已说明；节点父子关系、部件遮挡及坐标系明确；隐藏结构的推测与设计者已有决定分别标明。网页中的图片与 JSON 尺寸匹配，节点在原图坐标上对齐；验证拖动和保存后重新载入仍保持坐标与连接关系。交付网页和检查点项目；设计者尚未确认时只能标为 `awaiting_review`，阶段放行要求检查脚本返回 `0`。现有检查脚本验证数据及确认一致性，不代替人体语义完整性检查。

尚未提供原图或尚未完成的标注与分析如实列为缺项，不将未完成内容当作下一阶段的确定输入。
